2026.07.27 AI 制作フロー コスト設計

司令塔はコードを書かない
— AIエージェントのモデル分業とコスト設計

AIに何でも同じ深さで考えさせると、CSSの余白を1px直すだけの作業にも、システム全体の設計と同じだけの思考が費やされます。逆に、安く速いモデルに設計まで任せると、あとで全部やり直しになる。LiberaSpace では誰が考えて、誰が書くかを先に決め、そのうえでどれくらい深く考えるかを別の軸として調整しています。実際の設定と、分業がかえって損になる境目の話です。

01「全部いちばん賢く」が高くつく理由

AIに開発を任せはじめたとき、最初にやることはたぶん「いちばん賢いモデルを選ぶ」です。実際それで品質は上がります。ただ、しばらく使うと別の問題が見えてきます。

制作の作業は、ぜんぶが同じ難しさではありません。「この画面の余白を8px広げる」と「この業務をどうデータ構造に落とすか」は、必要な思考の量が二桁ちがう。それを同じ設定で処理すると、簡単な作業に、難しい作業と同じだけの時間とトークンを払い続けることになります。

かといって全部を安く速いほうに寄せると、今度は設計で事故ります。設計の失敗は、実装の失敗とちがってあとから静かに効いてくるのが厄介で、気づいたときには作り直しのほうが早い、という状態になっている。

前提

これは「どのモデルが優れているか」の話ではありません。同じ制作物の中に、要求される思考の深さが違う作業が混在しているという話です。だから答えも、モデルを1つ選ぶことではなく、作業ごとに割り当てることになります。

02司令塔・設計・実装に分ける

LiberaSpace では、ひとつの案件を3つの役割に分けています。

司令塔メインループ / 最上位モデル
やることは計画・分解・統合だけ。要件を受け取り、作業を2〜4個に割り、担当を決め、上がってきた成果物をつなぎ、最終報告をする。プロジェクトのソースコードは書きません。
設計・レビュー上位モデル / effort 高め
データ構造の設計、複雑なデバッグ、コードレビュー。間違えると後から高くつく判断をここに集めます。時間をかけてよい場所。
実装・雑務中位モデル / effort 中〜低
決まった設計どおりに書く、定型のマークアップ、テストの追加、リネームや整形。正解が既に決まっている作業はここ。速さと量が効きます。

ポイントは、分け方の基準を「作業の種類」ではなく「間違えたときの損失」に置くことです。実装は間違えてもテストで落ちるし、その場で直せます。設計の間違いは、10ファイル書いたあとに発覚します。だから設計に厚く配分する。

03なぜ司令塔はコードを書かないのか

この体制でいちばん反直感的なのが、いちばん賢い担当に手を動かさせない、という部分だと思います。もったいなく見える。

それでもこうしている理由は、手を動かし始めた瞬間に、全体が見えなくなるからです。ファイルを開いて実装に入ると、意識はその1ファイルの中に閉じます。人間のリーダーが自分でコードを書き始めると進捗管理が止まるのと、まったく同じことが起きる。

司令塔が担うのは、「この案件は何と何に分けられるか」「この2つは並行して進められるか」「上がってきた3つの成果物は噛み合っているか」という判断です。これは全体を俯瞰していないとできない仕事で、しかも案件を通じてずっと必要になる。ここに最上位を置くのが結局いちばん効きました。

副次的な効果もあります。司令塔が実装しないと決めると、作業を分解せざるを得なくなる。丸ごと一人にやらせる逃げ道が構造的に塞がるので、自然と並列化が進みます。

04思考の深さという、もうひとつの軸

モデルの選択とは別に、もうひとつ調整できる軸があります。同じモデルのまま、どれくらい深く考えるかを段階で指定する設定です。Claude では effort と呼ばれていて、low / medium / high / xhigh / max の5段階があります。

この2軸を混同すると設計を誤ります。整理するとこうです。

  • モデルの選択＝ 頭の良さの上限を決める。難しい問題を解けるかどうかに効く。
  • effort の選択＝ その頭をどれだけ使うかを決める。同じモデルでも、探索の量・確認の回数・出力の丁寧さが変わる。

実感としては、effort を下げるほうがモデルを落とすより副作用が小さい場面が多いです。短くて範囲の決まった作業なら低い effort で十分に速く、品質もそこまで落ちない。逆に、長時間の自律作業やコード全体に関わる判断は、モデルを上げるより先に effort を上げたほうが効くことがあります。

運用

まず high を基準に置き、案件ごとに上下に振って試すのがおすすめです。「とりあえず最大」は、思っているほど良くなりません。深く考えすぎて、簡単な作業を必要以上に複雑に解こうとすることがあります。

05モデルの階層と相場感

役割にどのモデルを当てるかの目安として、2026年7月時点の主要モデルを整理しておきます。金額は Anthropic の API 料金（100万トークンあたり）です。

モデルコンテキスト入力出力置きどころ
Claude Fable 51M$10$50最難関の長時間自律作業
Claude Opus 51M$5$25司令塔・設計・レビュー
Claude Sonnet 51M$3$15実装・テスト・雑務
Claude Haiku 4.5200K$1$5分類・整形など単純作業

2026年7月時点の Anthropic API 料金。Sonnet 5 には期間限定の割引価格が設定されている時期があります。最新の金額と提供状況は必ず Anthropic の公式ページでご確認ください。なお Claude Code を定額プランで使っている場合、この金額がそのまま請求されるわけではなく、利用枠の消費速度として効いてきます。

ざっくり言うと、出力トークンの単価は階層ひとつで2〜3倍動く。実装の担当を一段下げるだけで、量をこなす工程のコストは目に見えて変わります。逆に、設計とレビューは全体の作業量に占める割合が小さいので、ここを上位に置いてもトータルへの影響は限定的です。安くしたいなら、まず量が多い工程から下げるのが定石です。

06実際の設定

Claude Code の場合、既定のモデルと effort は設定ファイルに書けます。~/.claude/settings.json の実際の中身がこれです。

--- ~/.claude/settings.json（抜粋）
{
  "model": "opus[1m]",
  "effortLevel": "high"
}

これが「基準線」で、案件やその日の作業に応じて /model と /effort のコマンドで切り替えます。サブエージェント側は、定義ファイルごとに担当モデルを固定できます。前回の記事で紹介した制作ハーネスなら、検証担当は上位、実装担当は中位、といった具合です。

--- ~/.claude/agents/<name>.md
---
name: friday
description: 調べもの・文書作成・タスク整理などの汎用作業
model: sonnet
tools: Read, Write, Edit, Glob, Grep, Bash, WebSearch, WebFetch
---

1行 model: を書くだけで担当が固定されるので、その場の判断に任せず、体制として決めておけるのが大きいです。毎回「これはどのモデルでやるべきか」を考えるのは、それ自体がコストになります。

07分業が損になる境目

ここまで分業を推してきましたが、分けないほうが速い仕事もあります。むしろ、これを見誤ると全部が遅くなります。

分業には引き継ぎのコストがあります。担当を分けるということは、そのたびに「いま何をしていて、何が決まっていて、何を作ってほしいか」を説明し直すということです。上がってきた成果物を読んで統合する手間もかかる。この往復が、作業そのものより重くなる領域があります。

分けないほうがいい仕事

  • 数回のファイル読み書きで終わる作業。説明する時間で自分でやれる
  • 直前の文脈に強く依存する修正。引き継ぎで文脈が落ちて事故る
  • 探索的な調査。何を探すかが進めながら変わるので、指示を固定できない

分けたほうがいい仕事

  • 互いに独立していて、並行して進められる作業
  • 広い範囲を横断して読む調査。1つの担当が全部抱えると、肝心の判断のときに文脈が溢れる
  • 作った本人以外に見てほしい検証・レビュー

もうひとつ実際に踏んだ罠として、検証やレビューを分業しすぎないことも挙げておきます。「念のためもう一人に確認させる」を積み重ねると、確認のほうが本編より高くつきます。二重チェックが要るのは、間違えたときに戻せない作業だけで十分でした。

08安さは、直す時間まで含めて数える

この分業をやって、いちばん考え方が変わったのはコストの数え方でした。

1回の作業を安く済ませること自体には、あまり意味がありません。安いモデルに設計させて3回作り直したら、最初から上位で1回やったほうが安いし速い。逆に、量をこなすだけの実装を最上位でやり続けるのは、単に払いすぎです。

だから見るべきは、その工程を1回通したときの金額ではなく、完成まで持っていくのに何回通ったかのほうです。設計に厚く、実装に薄く配分すると、この「通した回数」が減ります。分業の目的は節約ではなく、やり直しを減らすことでした。

そしてこれは、AIに限った話でもないと思っています。誰に何を任せるかを決めて、間違えると高くつくところに時間を置く。やっていることは、普通のプロジェクトマネジメントとまったく同じでした。
