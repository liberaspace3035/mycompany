2026.07.27 AWS インフラ

AWSで動画販売サイトを本番運用する
— S3・CloudFront・Lightsail・SESの組み方と落とし穴

1本あたり最大20GBの動画をダウンロード販売するサイトを、AWS上で組みました。使ったのは S3・CloudFront・Lightsail・SES・IAM で、豪華な構成ではありません。それでも、買った人にだけ動画を渡すという一点を守るために、配信経路とアクセス権をかなり細かく設計する必要がありました。構成の考え方と、本番で実際に踏んだ落とし穴の記録です。案件の詳細は伏せ、技術的な内容だけを書いています。

01何を作ったか

会員登録して、動画を購入して、ダウンロードする。それだけのサイトです。ただし動画のサイズが大きく、1本あたり最大20GBを想定しました。そして当然ながら、買っていない人には渡してはいけない。この2つが構成のほぼ全てを決めています。

レイヤー採用したもの役割
アプリLaravel（PHP 8.4）購入・権限・ダウンロード回数の管理
サーバーLightsail（Ubuntu 24.04 / 2GB）nginx + PHP-FPM + MySQL + Redis + Supervisor
保管S3（東京・バージョニング有効）動画とサムネの保管。公開アクセスはブロック
配信CloudFrontサムネはOAC、動画は署名URL
メールAmazon SES購入通知・問い合わせ・自動返信
権限IAM構築用と運用用を2系統に分離
ドメインRoute 53 + certbotDNSとSSL（Let's Encrypt）

決済は PayPal（REST API + Webhook）。マネージドなコンテナ基盤やロードバランサーは使っていません。

02なぜ EC2 ではなく Lightsail か

AWSでWebアプリを本番運用すると聞くと、EC2 + ALB + RDS あたりを思い浮かべると思います。今回それを選ばなかったのは、この案件の規模に対して過剰だったからです。

想定される同時アクセスは多くありません。重い処理はすべてS3とCloudFrontに逃がしてあるので、アプリサーバーがやるのは購入処理と管理画面だけです。それに対してALBとRDSを立てると、月額がひと桁変わります。

Lightsail を選んだ理由は3つでした。

  • 月額が固定で読める。2GBメモリのプランで月12ドル。見積もりに載せやすく、クライアントにも説明しやすい
  • 1台に全部入る。nginx、PHP-FPM、MySQL、Redis、Supervisor（キューワーカー）、cron を1インスタンスに同居させています。この規模なら分ける理由がない
  • 引き継ぎやすい。普通のUbuntuサーバーなので、あとから別の人が触っても驚きが少ない

トレードオフ

当然、冗長化はされていません。このインスタンスが落ちればサイトは止まります。スケールアウトもできません。トラフィックが増えたら EC2 + ALB へ組み替える前提で、その判断ラインを最初に決めておく、という割り切りです。「将来のために今から分散構成にしておく」は、たいてい払い損になります。

静的IPは必ず割り当てる

Lightsail で最初に踏んだのがこれです。インスタンスを作っただけだと公開IPは動的で、再起動すると変わります。検証用のURLをクライアントに共有したあとにIPが変わり、「サイトが見られない」という連絡をもらって気づきました。

Networking から静的IPを作成してアタッチすれば固定されます。無料枠の範囲内（アタッチされている限り課金なし）なので、インスタンスを作ったらその場で必ず付けるのが正解です。

03配信を2系統に分ける — サムネはOAC、動画は署名URL

ここが設計の中心です。同じS3バケットに置いてあっても、サムネイルと動画では要求されるアクセス制御がまったく違います。

サムネイルCloudFront + OAC
商品一覧に出るので誰でも見られてよい。ただしS3バケット自体は非公開のまま保ちたい。→ Origin Access Control（OAC）で、CloudFront だけがオリジンを読める状態にする。
動画CloudFront + 署名URL
購入者だけ、しかも短時間だけ渡したい。→ trusted key group による署名付きURLを、アプリが購入状態を確認したうえで有効期限つきで発行する。

ポイントは、S3バケットのパブリックアクセスブロックは最初から最後まで有効のままだということです。バケットを公開して「URLを知っている人だけ」に頼るのは、URLが1度でも外に出た瞬間に終わります。実際、購入者が善意で共有リンクを貼ってしまうケースは十分ありえます。

署名URLの鍵はCloudFront側で作る

CloudFront の署名URLには、専用の鍵ペアが必要です。手順としてはこうなります。

# 1. 鍵ペアを作る
openssl genrsa -out private_key.pem 2048
openssl rsa -pubout -in private_key.pem -out public_key.pem

作った公開鍵を CloudFront コンソールの Public keys に登録して公開鍵IDを受け取り、それを Key groups にまとめます。あとは動画配信用ビヘイビアの Restrict Viewer Access を Yes にして、そのキーグループを指定するだけです。秘密鍵はアプリ側が署名生成に使います。

秘密鍵は絶対にリポジトリに入れないこと。これを入れてしまうと、鍵の意味が丸ごと消えます。

なぜ S3 の署名URLではなく CloudFront の署名URLか

S3にも署名URLの仕組みがありますが、それだとCDNを経由せず配信することになります。大きなファイルをエッジから配信しつつ、アクセス制御もかけたい——両立させたいなら CloudFront 側で署名する必要があります。20GBのファイルを毎回オリジンから引くのは、速度的にも転送コスト的にも避けたい構成です。

0420GBの動画を、ブラウザから直接S3へ

管理者が動画をアップロードする側の話です。ここは早い段階で「アプリサーバーを経由させない」と決めました。

20GBのファイルをPHPで受け取ろうとすると、まず upload_max_filesize と post_max_size の壁があり、次にリクエストタイムアウトの壁があり、さらに一時ファイルを置くディスク容量の壁があります。2GBのLightsailインスタンスでは、そもそも置き場所がありません。

採ったのは、ブラウザから直接S3へマルチパートアップロードする方式です。1パート64MBで分割して送ります。アプリサーバーは、アップロード先の署名だけを発行して、あとは関与しません。

この方式で必要になるのが2つあります。

1. S3バケットのCORS設定

ブラウザから直接PUTするので、当然クロスオリジンになります。許可オリジンに本番ドメインを入れておかないと、開発環境では通ったのに本番で全部弾かれる、という事故になります。今回はこの設定を artisan コマンド化して、ドメインを引数で渡すだけにしました。

php artisan infra:setup-bucket-cors --origin=https://(本番ドメイン)

2. IAMのマルチパート系アクション

これが忘れやすい。PutObject だけでは足りません。マルチパートアップロードには専用のアクションが必要です。

"Action": [
  "s3:PutObject", "s3:GetObject", "s3:DeleteObject", "s3:ListBucket",
  "s3:ListBucketMultipartUploads",
  "s3:ListMultipartUploadParts",
  "s3:AbortMultipartUpload"
]

特に AbortMultipartUpload は、アップロードが途中で失敗したときの後始末に使われます。これが無いと、中断された不完全なパートがバケットに残り続けて課金されます。動くかどうかのテストでは気づきにくく、請求で気づくタイプの漏れです。

05SESの本当の壁はサンドボックス

メール送信に SES を使いました。設定自体は難しくありません。ドメインを登録して、Easy DKIM を有効にして、表示されるCNAMEをDNSに入れるだけです。

問題は、新規のSESアカウントは全てサンドボックス状態から始まることです。この状態には2つの制限があります。

  • 検証済みのアドレス宛にしか送れない（送信先を1つずつ登録する必要がある）
  • 24時間あたり200通まで

本番運用にはまったく足りないので解除申請が必要なのですが、そこに至るまでに2つ事故りました。

事故1：メール確認を有効にすると、誰も登録できなくなる

新規登録時にメールアドレス確認を必須にする機能があります。これを本番で有効にすると、どうなるか。

新規登録者のアドレスは、当然まだSESに検証登録されていません。つまり確認メールが送信拒否される。届かないので確認できず、確認できないので登録が完了しない。サンドボックス中は、この機能を有効にした瞬間に新規登録が完全に不能になります。

対処は単純で、サンドボックス解除が承認されるまでメール確認機能は無効のままにする。承認後に有効化する、と決めておくだけです。ただ、これは事前に気づかないと「登録できません」という問い合わせで発覚します。

事故2：1通の中に未検証アドレスが混ざると、全員に届かない

問い合わせがあったとき、管理者全員に通知メールを送る実装にしていました。コードにするとこうです。

// 管理者全員を宛先にして「1通」送る
Mail::to($admins->all())->send(new ContactNotification($contact));

これはSESのサンドボックス下で危険です。宛先リストの中に未検証のアドレスが1つでも含まれていると、その送信リクエスト全体が拒否されます。結果、同じ宛先リストに入っていた検証済みのアドレスにも届きません。

管理者を1人追加しただけで、それまで届いていた通知が全部止まる。原因が「追加した人」ではなく「送り方」にあるので、調べ始める場所を間違えやすい事故でした。

// 宛先ごとにループして送れば、失敗を1件に閉じ込められる
foreach ($admins as $admin) {
    try {
        Mail::to($admin)->send(new ContactNotification($contact));
    } catch (\Throwable $e) {
        report($e); // 1件失敗しても他は送る
    }
}

あわせて、問い合わせの本文は必ずDBに保存して管理画面から読めるようにしました。メールはあくまで通知手段で、記録の本体ではない。この分離をしておくと、送信が失敗しても内容だけは確実に残ります。

解除申請と、送信元ドメイン

サンドボックス解除は、SESコンソールの Account dashboard から Request production access で申請します。用途（Transactional）、サイトURL、連絡先を書いて送ると、初回の応答は24時間以内に来ます。

あわせて注意したいのが送信元です。検証を通すだけなら Gmail などのアドレスでも送れてしまうのですが、受信側のDMARC判定で迷惑メール扱いになりやすい。本番ドメインが決まったら、ドメイン検証とDKIMを設定して、送信元をそのドメインのアドレスに揃えるべきです。

06IAMは「構築用」と「運用用」に分ける

AWSでいちばん危ないのは、作るための強い権限を、そのままアプリに持たせてしまうことだと思っています。今回は最初から2系統に分けました。

構築用一時的・管理者相当
S3バケット、CloudFrontディストリビューション、Lightsailインスタンス、SESの設定を作るための権限。構築が終わったら外す。
アプリ運用用最小権限・.env に入れる
対象バケットへのS3操作と、SESの送信のみ。これしか持っていなくてもアプリは動くことを確認したうえで納品する。コンソールログインは付けない。

運用用のポリシーは、リソースを対象バケットに限定します。

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "S3VideoBucket",
      "Effect": "Allow",
      "Action": [
        "s3:PutObject", "s3:GetObject", "s3:DeleteObject", "s3:ListBucket",
        "s3:ListBucketMultipartUploads", "s3:ListMultipartUploadParts",
        "s3:AbortMultipartUpload"
      ],
      "Resource": [
        "arn:aws:s3:::(バケット名)",
        "arn:aws:s3:::(バケット名)/*"
      ]
    },
    {
      "Sid": "SESSend",
      "Effect": "Allow",
      "Action": ["ses:SendEmail", "ses:SendRawEmail"],
      "Resource": "*"
    }
  ]
}

そして納品前に必ずやることが2つあります。構築用の権限を外すことと、アクセスキーをローテーションすることです。

特に後者。開発中、認証情報をチャットやメールで受け渡すことは現実にはあります。その瞬間に、そのキーは「漏れた可能性がある」ものとして扱うべきです。動いているから大丈夫、ではなく、納品のタイミングで機械的に作り直す。手順書のチェックリストに入れておかないと、まず忘れます。

07デプロイで踏んだ4つの落とし穴

ここからは、AWSというより Ubuntu + nginx + PHP-FPM の運用で踏んだものです。どれも原因が分かれば一瞬ですが、分かるまでが長かった。

1. .env の所有権が変わって、全ページ500

これが最悪でした。サーバー上で .env をちょっと直そうと、ubuntu ユーザーで sed -i をかけた。それだけです。

ところが sed -i はファイルを書き換えるのではなく、作り直します。結果、所有グループが www-data から ubuntu に変わる。.env のパーミッションは 640 なので、グループが変わった瞬間に php-fpm（www-data）が読めなくなります。

そこから先の壊れ方が分かりにくい。環境変数が全部NULLになり、設定が全部デフォルト値になり、DB_CONNECTION が未設定なので SQLite にフォールバックし、存在しないSQLiteファイルを掴んで全ページ500。ログに出るのは SQLiteConnector のエラーです。MySQLの設定は1文字も変えていないのに。

# 切り分け：www-data から見て何が見えているか
sudo -u www-data php artisan about   # Database が sqlite なら確定
sudo -u www-data head -c1 .env       # そもそも読めるか

# 対策：.env を触ったら必ず所有権を戻す
sudo chown ubuntu:www-data .env && sudo chmod 640 .env

2. reload では設定が反映されない

本番のPHPは opcache.validate_timestamps=0 にしています。ファイルの更新時刻を毎回見に行かない設定で、性能のためには正しい。ただしこれは、ファイルを更新しても自動では反映されないということでもあります。

コードを更新したときは systemctl reload php8.4-fpm で足ります。しかし環境変数やPHP側の設定を変えたときは、reload では反映されませんでした。restart が必要です。

厄介なのは、コマンドがエラーを出さないことです。「デプロイは成功した、でも変更が反映されていない」という、いちばん疑いにくい状態になります。

3. route:cache の実行順序

Laravel のキャッシュ再構築で、いきなり route:cache を叩くと失敗します。

Argument #1 must be of type RouteCollection, CompiledRouteCollection given

すでにキャッシュ済みの状態から再キャッシュできない、という制約です。clear を全部先に流してから cache を流すのが正解でした。

sudo -u www-data php artisan route:clear
sudo -u www-data php artisan config:clear
sudo -u www-data php artisan view:clear
sudo -u www-data php artisan config:cache
sudo -u www-data php artisan route:cache
sudo -u www-data php artisan view:cache
sudo systemctl reload php8.4-fpm

そしてこれを && で1行に繋いでいると、途中で失敗した時点で最後の reload まで実行されません。「エラーは見えたけど、まあ再実行すればいいか」で流すと、古いコードが動き続けます。落とし穴1と組み合わさると原因追及が一気に難しくなります。

4. artisan を叩くユーザーを間違える

同じ php artisan でも、コマンドによって実行すべきユーザーが違います。

  • key:generate は ubuntu で実行。.env に書き込むため。www-data だと書けず、APP_KEY が空のまま500になります
  • キャッシュ系（config:cache など）は sudo -u www-data で実行。storage/logs が www-data 所有なので、ubuntu で叩くと Permission denied になります

「artisan は全部 sudo で」でも「全部 ubuntu で」でも駄目で、コマンドごとに使い分ける必要がありました。これは手順書に書いておかないと、次に触る人が確実に踏みます。

08課金は誰が持つか — アカウントをまたぐ移管

最後に、技術というより体制の話です。この案件では開発中は自社のAWSアカウント、本番はクライアントのAWSアカウントという形をとりました。

理由は単純で、AWSの課金と責任はサービスのオーナーが持つべきだからです。開発者のアカウントに本番環境を置いたままにすると、請求書は開発者に届き続けます。障害が起きたときの責任範囲も曖昧になる。何より、あとで移そうとしたときのほうが大変です。

そのため、本番公開の段階でクライアントのアカウント側に全部作り直しました。S3バケット、CloudFrontディストリビューション、Lightsailインスタンス、SESの設定。アプリ側は .env の値を差し替えるだけで動くようにしてあります。

この移管を安全にやるために、2つ用意しました。

  • 手順書。IAMの準備からキーローテーションまで10手順を文書化し、各手順にAWS公式ドキュメントのURLと参照日を付けました。AWSはコンソールのUIが頻繁に変わるので、「どの版を見て書いたか」が残っていないと1年後に読めなくなります
  • 構築コマンド。CloudFront作成・CORS設定・Lightsail作成・SES状態確認を artisan コマンドにしてあります。手順書の中で「ここはこのコマンド」と書けるので、コンソールでの手作業を減らせます

それと、手順書には「公式で裏が取れていない項目」を明記した節を作りました。署名URLの鍵をアプリがどの設定キーで読むか、certbot の正確な手順、IAMポリシーの過不足など。分かっていないことを分かっていないと書いておくほうが、あとから読む人にとっては安全です。

公開前に必ず外すもの

検証中はサイト全体に Basic認証をかけ、X-Robots-Tag: noindex を付けていました。公開前にこれを外すのを忘れると、決済のWebhookが401で弾かれ、かつ検索エンジンにも載りません。手順書の公開前チェックリストに入れておくべき項目です。

09小さく作って、境界だけ厳密に

この構成を振り返って思うのは、お金をかけるべきところと、かけなくていいところがはっきり分かれていたということです。

サーバーは月12ドルの1台で足ります。冗長化もオートスケールもしていません。一方で、「買った人だけが動画を取得できる」という境界の設計には手を抜きませんでした。バケットは非公開のまま、配信はCloudFront経由、動画は期限付きの署名URL、権限は最小限のIAM。ここだけは削れません。

逆の作り方——立派な分散構成を組んだうえで、バケットを公開してURLを知っている人だけに頼る——のほうが、費用も高く、危険です。構成の規模と、守るべき境界の厳密さは、別々に決めていい。それがいちばんの収穫でした。

AWS構成のご相談

規模に合った構成の選定から、S3・CloudFrontを使った配信設計、本番移管とセキュリティ整理まで対応しています。「どこまで作り込むべきか分からない」段階でのご相談も歓迎です。
