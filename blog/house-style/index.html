ハウススタイルを固定して量産する
— 中小企業向け業務アプリ7本の作り方

AIに毎回ゼロから「いい感じのアプリを作って」と頼むと、毎回ちがうものが出てきます。ファイル構成も、データの持ち方も、ボタンの角丸まで違う。1本目は問題なくても、3本目には自分でどれがどれか分からなくなります。LiberaSpace では変えない部分を先に全部決めて、業務ロジックとアクセント色だけを差し替えることにしました。この型で実際に7本つくった記録です。

01毎回ちがうものが出てくる問題

AIに小さなアプリを作らせるのは、いまや簡単です。要件を書けば、動くものがその日のうちに出てきます。問題は2本目からで、同じ人が同じ道具で作ったはずなのに、まるで別のチームの成果物になる。

データを localStorage に入れるものと IndexedDB を使うものが混ざる。CSSの命名規則が違う。テストがあるものとないものがある。どれも単体では正しいので、指摘のしようもありません。ただ、こちらが後から手を入れるときに毎回読み直しが発生します。

原因ははっきりしています。毎回ゼロから最適解を考えさせているからです。同じ条件でも、AIは毎回わずかに違う設計に着地します。人間でもそうです。

だから、考えさせる範囲を減らすことにしました。「業務が違う部分」だけを考えさせ、それ以外は全部こちらが決め打ちする。この線引きをはっきりさせたら、量産が一気に安定しました。

02つくった7本

作っているのは、中小企業の現場でそのまま使える小さな業務アプリです。1フォルダ＝1アプリで、それぞれ別々の業務課題を扱います。

Vol.名前扱う業務
01スッと請求書インボイス対応の請求書・見積書
02シフトめいとシフトの自動作成
03在庫番在庫・発注・期限管理
04予約上手予約・担当×時間のタイムライン・ダブルブッキング検出
05おかね帳現金出納帳・複数口座・振替・経費集計
06だんどりタスク／案件のカンバン
07てんけん設備保守・定期点検

新しい Vol. を足すときは、既存と業務課題が重ならないものを選びます。似た課題を2本作ると、どちらを案内すべきか自分でも判断できなくなるためです。

03先に決めた、動かさない前提

全部のアプリに共通する前提を、最初に固定しました。ここは案件ごとに考え直しません。

  • 完全にブラウザの中だけで動く。サーバーもデータベースも使いません
  • データは localStorage のみ。外部にはいっさい送信しない
  • 登録不要・無料・依存ゼロ。フレームワークもビルド時の外部パッケージも使わない
  • 日本語UI・レスポンシブ・印刷対応・CSV出力・JSONバックアップを全部に備える

この前提は、技術的な好みで決めたわけではありません。想定している使い手から逆算した結果です。

中小企業の現場でいちばん強い抵抗にあうのは、「アカウントを作ってください」と「データはクラウドに保存されます」の2つでした。特に、売上や人名が入るアプリでは顕著です。端末の中だけで完結すると言い切れると、この会話が丸ごと消えます。

副次的な効果として、この制約が実装をきれいにします。認証もサーバーもないので、AIが考える範囲が業務ロジックとUIだけに絞られる。悩みどころが減るぶん、精度も安定しました。

トレードオフ

もちろん万能ではありません。複数人でのリアルタイム共有はできませんし、端末が変わればデータは移りません（JSONバックアップの書き出し／読み込みで手動移行します）。「一人か少人数が、一台で使う業務」に絞ると決めたうえでの設計です。

04構成とデザイントークンを型にする

ファイル構成も固定です。どの Vol. を開いても同じ場所に同じものがあります。

Vol.N/
├── index.html
├── css/styles.css
├── js/            ← ES Modules で6ファイル
│   ├── util.js         汎用ヘルパー
│   ├── (domain).js     業務ロジック
│   ├── sample.js       サンプルデータ
│   ├── store.js        localStorage の読み書き
│   ├── ui.js           描画とイベント
│   └── app.js          起動
├── test/*.test.mjs  ← node で実行
├── build.mjs        ← 単体HTMLを生成
├── start.command
└── README.md

この分け方がAIに伝わりやすいのは、「どのファイルを触るべきか」が名前だけで決まるからです。「税率の計算がおかしい」なら業務ロジックのファイル、「一覧の並び順を変えたい」なら ui.js。指示が短くて済むうえに、関係ないファイルを巻き込む事故が減ります。

CSSも同じ考え方で、デザイントークンを共通化して、色のスケールだけを Vol. ごとに変えます。以下は Vol.7（てんけん）の実際の冒頭です。

/* ============ てんけん — styles ============ */
:root{
  /* ここだけ Vol. ごとに変える */
  --brand-500:#06b6d4; --brand-600:#0891b2; --brand-700:#0e7490;

  /* 以下は全 Vol. 共通 */
  --ink:#0c1a1e; --line:#dde9ec; --bg:#f0f5f6; --surface:#ffffff;
  --shadow:0 4px 6px -1px rgba(8,30,35,.08), 0 2px 4px -2px rgba(8,30,35,.06);
  --r:12px; --r-sm:8px; --r-lg:18px;
  --sans:"Hiragino Kaku Gothic ProN","Hiragino Sans","Yu Gothic",Meiryo,system-ui,sans-serif;
}

角丸・影・文字色・区切り線・フォントは全部共通。変えるのはブランドカラーのスケールだけです。Vol.2 は teal、Vol.3 は indigo、Vol.7 は cyan、という具合に振り分けています。

効果は見た目の統一だけではありません。「デザインをどうするか」という一番ブレる工程を、AIの判断範囲から外せるのが大きい。放っておくと、角丸カードと青いボタンが並ぶ「いかにもAIが作った画面」に収束していきます。トークンを先に渡しておけば、その余地はなくなります。

05ダブルクリックで動く1ファイルに固める

開発中は ES Modules で分割していますが、納品するのは1個のHTMLファイルです。node build.mjs が import と export を取り除いて連結し、てんけん.html のような日本語名の単体ファイルを出力します。サイズは1本あたり76KB〜124KBほどです。

この一手間を入れている理由は、渡した相手が確実に開けるからです。

  • ダブルクリックすれば、そのままブラウザで開く。サーバーもインストールも不要
  • メールに添付できる。USBメモリでも渡せる
  • ファイルが1個なので、「フォルダごと移動しないと壊れる」が起きない

ES Modules のままだと、ローカルの file:// で開いたときに読み込みがブロックされます。技術者なら簡易サーバーを立てればいい話ですが、渡す相手にそれを求めた時点で使われなくなります。ビルドを1工程はさむのは、ひとえにそのためです。

なお、このビルドスクリプトでは置換処理の落とし穴を実際に踏みました。詳細はメモリー運用の記事に書いていますが、String.replace の置換文字列に $$ が含まれると壊れる、というものです。

067本つくって分かったこと

1本目と2本目は、作り方が違ってよかった

Vol.1 だけは Planner / Generator / Evaluator の制作ハーネスを通して作りました。仕様書を書き、実装し、ブラウザで検証する流れです。フォルダの中身も他と違い、SPEC.md と EVAL.md が残っています。

そこで型そのものを作ったので、Vol.2 以降は型に乗せるだけになりました。ハーネスは「まだ型がないものを作る」ときに効き、型ができたあとは軽い流れのほうが速い。同じ道具をずっと使い続ける必要はありませんでした。

テストとビルドを毎回必ず通す

各 Vol. は node test/*.test.mjs と node build.mjs を必ず通してから完成にします。派手な仕組みではありませんが、「動いてるように見えるけど単体HTMLでは壊れている」を確実に潰せるのがこの工程です。分割状態では動いてビルド後に壊れる、という事故が実際にありました。

レビューは「壊しに行く」担当を別に立てる

完成後には、意図的に穴を探すレビューを別途かけています。出てきた指摘には、たとえば次のようなものがありました。

  • 取り込んだJSONのID文字列に、属性を抜け出すような値が入る可能性の対策
  • CSV出力時の数式インジェクション対策（ただし、純粋な数値と負数まで巻き込まないこと）
  • 先入先出の期限計算を、単純な残数の引き算ではなく時系列の再生で行う（その時点で在庫があったロットだけを消費する）

いずれも、通常の動作確認では表面化しません。作る流れと壊す流れは、別の工程として持っておく必要がありました。

「次に何を作るか」がいちばん難しい

意外にも、実装より題材選びのほうが悩みます。既存7本と重ならず、かつ実際に困っている人がいる業務。いまの候補は、簡易勤怠、問い合わせ・クレーム管理、回数券やスタンプカードあたりです。型があると実装は速いので、価値の判断のほうがボトルネックになります。

07型は、AIのためではなく人のためにある

ハウススタイルを固めると聞くと、AIに指示しやすくするための工夫に見えるかもしれません。実際、その効果はあります。ただ、7本作ってみていちばん効いたのは、そこではありませんでした。

後から自分が手を入れられることです。3か月前に作った Vol.3 に修正依頼が来ても、開けば同じ場所に同じものがある。読み直しがいりません。AIに渡すときも「いつもの構成です」で通じます。

逆に言えば、型を持たないまま量産すると、作った本数だけ保守できない資産が増えます。速く作れることと、増やし続けられることは別の能力でした。AIで制作を速くしたいなら、速さより先に決めておくべきことがある。これがいまのところの結論です。

業務に合わせた小さな道具、つくります

ここで紹介したアプリはすべて、端末の中だけで完結する構成です。「うちの業務にはこれが足りない」があれば、同じ考え方で個別におつくりできます。まずはお気軽にご相談ください。
