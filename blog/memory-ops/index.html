同じバグを二度踏ませない
— プロジェクト単位のメモリー運用

AIとの作業でいちばんもったいないのは、前回半日かけて解決した問題を、次のセッションでまた半日かけて解決することです。会話が終われば文脈は消えるので、放っておくと必ずそうなります。防ぐ方法はひとつしかなくて、その場で外に書き出しておくこと。LiberaSpace が実際にどう書き残しているかと、実際に残っている落とし穴の中身を公開します。

Contents

01セッションが変われば、全部忘れる

AIとの作業は、ひとつの会話の中でならどんどん賢くなります。プロジェクトの構造を把握し、こちらの好みを覚え、さっき踏んだ失敗を避けるようになる。そこまでは快適です。

問題は、その会話が終わったときです。次に開いた新しいセッションは、まっさらな状態から始まります。プロジェクトのファイルは読めば分かりますが、「なぜこの実装になっているか」「前回どこでハマったか」は、コードのどこにも書かれていません。

結果として何が起きるか。前回と同じ落とし穴に、同じ手順で落ちます。しかも本人（AI）に自覚がないので、こちらが「それ前もやった」と気づくまで進みます。ここで失われる時間が、実際いちばん大きい。

前提

これはAIの性能の問題ではありません。会話の外に記録がないなら、次の会話が知りようがないという、ただの構造の話です。だから対策も、賢いモデルを選ぶことではなく、書き出す仕組みを作ることになります。

021ファイル1事実で書く

Claude Code にはプロジェクトごとのメモリー領域があります。LiberaSpace ではそこに、1ファイル＝1つの事実という粒度で書き残しています。長い議事録を1本作るのではなく、小さいメモをたくさん置く形です。

  type: reference
---

（ここに本文）

先頭に description を必ず1行入れているのが肝で、これは「この記憶は今の作業に関係あるか」を判断するためだけの行です。全部の本文を読まなくても、この1行で拾うか捨てるかが決まる。メモが増えても邪魔にならないのは、この仕組みのおかげです。

そして、粒度を小さく保つ理由がもうひとつあります。1ファイル1事実にしておくと、間違っていたときに消せる。長い文書に埋め込んでしまうと、一部だけ古くなったときに手が出せなくなります。

種類も分けています。ユーザー本人のこと、仕事の進め方への指摘、プロジェクトの状況、外部リソースの場所。このうち「進め方への指摘」は必ず理由まで書くようにしていて、これは理由が分からないルールが一番早く形骸化するからです。

以下、実際に残しているメモの中身をそのまま2つ紹介します。どちらも中小企業向けの業務アプリを作っている最中に踏んで、原因の特定に時間を持っていかれたものです。

03実例1：置換文字列で $$ が消える

作っているアプリは、最終的にダブルクリックだけで動く単体HTMLに固めています。ビルドスクリプトが JavaScript を1本に連結し、HTMLの中に埋め込む、という単純な処理です。

その埋め込みを、こう書いていました。

// 動かない
html.replace(tag, `<script>${bundle}</script>`);

これで生成したHTMLが、構文エラーで動きません。しかも壊れ方が奇妙で、元のJSファイル単体では正常に動く。連結したときだけ壊れる。

原因は String.prototype.replace の仕様でした。置換文字列の中では $ が特殊な意味を持ちます。$& はマッチした文字列全体、$$ は $ そのものを表す記号です。つまり——

コードの中に const $$ = document.querySelectorAll... のような変数があると、置換の過程で $$ が $ 1文字に化けます。以降その変数は未定義になり、構文エラーになる。DOM操作でよく使う書き方なので、まともに踏みました。

直し方は簡単で、置換文字列ではなく関数を渡す。関数の戻り値は特殊記号として解釈されません。

// 動く — 関数で返せば $ は特殊記号にならない
html.replace(tag, () => `<script>${bundle}</script>`);

知っていれば5分、知らなければ半日溶けるタイプの罠です。そしてこの手のものこそ、記憶しておく価値がある。設計判断とちがって毎回ゼロから考え直す意味がなく、ただ知っているかどうかで決まるからです。

04実例2：stopPropagation でボタンが死ぬ

もうひとつは、クリック処理の設計を誤ったケースです。

一覧表示のある画面で、こういう構成にしていました。document.body にクリックのリスナーを1つだけ置き、closest('[data-act]') で「押されたのはどのアクションか」を判定する。いわゆるイベント委譲です。要素が増えてもリスナーは1個で済む、素直な設計です。

ここで、行そのものがクリック可能（<tr data-act="open">）で、行の中にボタン（<button data-act="delete">）もある、という形にしたかった。ボタンを押したときに行のクリックまで発火すると困るので、こう書きました。

// ボタンが無反応になる
<td onclick="event.stopPropagation()">
  <button data-act="delete">削除</button>
</td>

結果、ボタンが完全に無反応になりました。当然で、リスナーは body にしかいないのに、その手前で伝播を止めているからです。行の誤発火は防げましたが、ボタンのクリックも一緒に殺していました。

そして正解は、何もしないことでした。closest() は「いちばん近い」祖先を返します。ボタンをクリックすれば、closest('[data-act]') が最初に見つけるのはボタン自身であって、外側の <tr> ではない。行アクションとボタンアクションは、放っておけば自然に両立します。

// これでいい。stopPropagation は不要
<td>
  <button data-act="delete">削除</button>
</td>

教訓

1つめは知識で防ぐ罠、2つめは設計の勘違いで作り込んだ罠です。厄介なのは後者で、こちらは「防ごうとした対策そのものが原因」になっている。直した経緯まで書き残しておかないと、次も同じ理由で同じ対策を入れます。

05何を書き、何を書かないか

やってみて分かったのは、書きすぎると使われなくなるということでした。メモが多すぎると、どれが今の作業に関係あるか判断できなくなり、結局全部無視されます。だから、書かないものを決めておくほうが重要です。

書かないもの

  • コードを読めば分かること。ディレクトリ構成、関数の役割、使っているライブラリ。これは読ませればいい
  • Git の履歴に残っていること。いつ何を直したかは、コミットログのほうが正確です
  • その会話でしか意味を持たないこと。「今日はここまで」のような進行メモ

書くもの

  • 踏んだ罠と、その回避方法。上の2例のような、知識で防げるもの
  • 指摘されて直した進め方と、その理由。理由がないと次に別の形で再発します
  • コードに現れない制約。「この環境ではホスト側でビルドできない」「デプロイ先は公開リポジトリにしない」など
  • 相対日付を絶対日付に直したもの。「来週」は1か月後に読むと意味不明になります

ひとことで言うと、リポジトリを見れば分かることは書かず、リポジトリに現れないものだけを書く。この線引きに落ち着きました。

もうひとつ、運用上の注意があります。間違っていたと分かったメモは、その場で消すこと。古い記憶は、無いより悪い。存在しなくなったファイル名やコマンドを参照し続けて、遠回りの原因になります。書き足すのと同じ頻度で、消す作業も必要です。

06資産になるのは、コードではなく判断

この運用を続けて感じているのは、案件を重ねて溜まっていく本当の資産は、コードそのものではないということです。コードは案件ごとに違うし、フレームワークが変われば書き直します。

残るのは、「この方法は前に試して駄目だった」という判断のほうでした。それはコードには書かれていないし、書いた本人が忘れれば消えます。人間のチームだと、それが暗黙知としてなんとなく共有されていく。AIと組むなら、明示的にファイルにしておくしかない。

手間に見えますが、実際にかかるのは1件あたり数分です。それで次の半日が守れるなら、悪くない取引だと思っています。
