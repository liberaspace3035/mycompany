2026.07.27 AI 制作フロー Claude Code

作らせて、検証させる
— Claude Code の3エージェント制作ハーネス

AIにWebサイトを作らせると、たいてい「動いてそう」で止まります。画面はできている、コードも読める、でも本当にクリックが通るのかは誰も確かめていない。LiberaSpace ではこの「そう」を消すために、Claude Code のサブエージェントを Planner / Generator / Evaluator の3役に分け、実際のブラウザで受け入れ条件を1つずつ踏み直すところまでを1本の流れにしています。この記事は、その構成と、実際に案件で回してみて分かったことの記録です。

Contents

01「動いてそう」はどこで生まれるか

AIに1体で「このサイトを作って」と頼むと、同じAIが仕様を決め、実装し、最後に自分で「できました」と判定します。この3つを1体でやることが問題の根っこです。

まず、仕様が実装の途中で静かに動きます。作りながら「ここはこうした方が自然だ」と判断が入り、最初に想定していたものと少しずつズレる。ズレたこと自体は悪くないのですが、どこがズレたのかの記録が残りません。

そして最後の判定が甘くなります。自分が書いたコードを自分でレビューして「問題ありません」と言うのは、人間でも難しい。AIはさらに素直なので、読んで筋が通っていれば通ったことにします。ボタンを実際に押してはいません。

結果として出てくるのが「動いてそうなもの」です。納品してから、モバイルで横スクロールが出る、コンソールがエラーで埋まっている、フォームのボタンが無反応、といった形で発覚します。

前提

これは「AIの精度が足りない」という話ではありません。設計・実装・検査を同じ主体がやると品質が落ちるのは、人間の開発現場でもずっと同じです。だから解決策も同じで、役割を分ける。

02役割を3つに割る

Claude Code には、専用の役割・専用のツールセットを持たせたサブエージェントを自分で定義する仕組みがあります。~/.claude/agents/ に Markdown ファイルを1枚置くだけで、名前・使えるツール・振る舞いを固定した「担当者」を作れます。

LiberaSpace ではここに3体を置いています。

PlannerRead / Glob / Grep / Write
1〜4行のアイデアを、実装可能な仕様書 SPEC.md に展開する。書けるのは仕様だけ。実装ツールを持たせていないので、コードには触れません。
GeneratorRead / Write / Edit / Glob / Grep / Bash / Skill
仕様書のうち、今回のスプリントに入っている機能だけを実装する。仕様書そのものは書き換えない。
EvaluatorPlaywright MCP / Read / Bash
できたものを実際のブラウザで操作して合否を出す。Generator のコードには絶対に触らない。直す権限を持たないので、判定が甘くなる動機がありません。

肝はツールの与え方です。「仕様を書き換えないでね」とお願いするのではなく、Planner に Edit を渡さない。「勝手に直さないでね」ではなく、Evaluator に Write を渡さない。指示は破られることがありますが、持っていない道具は使えません。

--- ~/.claude/agents/website-evaluator.md
---
name: website-evaluator
description: Generator が作った ./site/ を実機ブラウザで動かし、
  ./SPEC.md の受け入れ条件を検証して合否を判定する。
tools: Read, Glob, Grep, Bash, Write,
  mcp__playwright__browser_navigate,
  mcp__playwright__browser_click,
  mcp__playwright__browser_console_messages,
  ...
---

03Planner — 曖昧語を仕様から追い出す

Planner の仕事は「何を作るか」を徹底的に言語化することだけです。機能を漏れなく並べ、依存関係を見てスプリントに割り、それぞれに「ユーザーが何をできれば合格か」を書く。出力は必ずプロジェクト直下の SPEC.md に落ちます。

ここで2つ、強く禁じていることがあります。

技術的な実装詳細を書かせない

DBスキーマ、ライブラリ選定、関数設計は書かせません。理由は単純で、仕様で間違えると、下流のGeneratorとEvaluatorにそのまま伝播するからです。仕様書に書かれた「間違った設計」は、下流から見ると与件になってしまい、誰も疑いません。実装の判断は実装する側に残しておく方が、事故が小さく済みます。

曖昧な機能名を許さない

「いい感じのUI」「使いやすいフォーム」は禁止語です。この手の言葉は、書いた時点では合意できているように見えて、検証の段になって初めて「誰も合否を判定できない」ことが分かります。受け入れ条件は、Evaluator がブラウザでそのまま再現できる粒度まで落とします。

機能IDは F-01, F-02 …、スプリントは Sprint 1, Sprint 2 … と一意に採番し、一度振ったIDは付け替えません。あとで「F-07が落ちている」という会話を、人間とAIの両方が同じ意味で扱えるようにするためです。

04Generator — 今回のスプリントだけ作る

Generator は SPEC.md を読み、指定されたスプリントの機能だけを ./site/ に実装します。原則1回1機能から積み上げる。「ついでにここも直しておきました」をやらせないのが大事で、スコープ外の変更は、Evaluator の判定範囲の外側で壊れる原因になります。

もう1つ、この工程には見た目の問題があります。放っておくといかにもAIが作った見た目—— 中央寄せ、角丸カード、青いボタン、均一な余白 —— に収束していく。そこで Generator には、UIに手を付ける前にデザイン系のスキルを必ず通させています。スプリント開始時に配色・タイポ・スタイルの方針を固めてから実装に入る、という順番を固定するだけでも、既定値に落ちる確率はかなり下がります。

既存ページに機能を足すときは、既存のデザイン言語（配色・間隔・コンポーネント）に合わせる。新しいスタイルを混ぜない。これも明文化しておかないと、スプリントごとに少しずつ違うサイトになります。

境界

スキルはあくまで品質を上げる手段で、受け入れ条件やスプリント範囲を超える権限は与えていません。スキル側が良い提案をしてきても、スコープ外なら採用しない。仕様を変えたくなったら Planner に差し戻します。

05Evaluator — 実機で踏み直す

ここがこのハーネスの本体です。Evaluator は Playwright MCP を通じて実際のブラウザを立ち上げ、SPEC.md の受け入れ条件を1つずつ、ユーザーがやる操作そのままの順序で再現します。クリック、入力、画面遷移、表示確認、そしてリロード後もデータが残っているかまで。

それに加えて、案件によらず毎回見る観点を固定しています。

  • コンソールに error / warning が出ていないか
  • ネットワークに 4xx / 5xx がないか
  • 375 / 768 / 1280px で主要画面が崩れていないか（横スクロールの発生有無）
  • キーボード操作とラベル付与など、基本のアクセシビリティ

そして各観点に閾値を先に決めておき、1つでも下回ったらそのスプリントは不合格にします。「まあ許容範囲かな」という判断が入る余地を、判定の前に潰しておく。閾値を緩める判断は、Evaluator に単独でさせません。

細かいところですが、効きが大きかった一文があります。

Evaluator の定義より

Playwright MCP が未導入なら、検証不能である旨を最初に報告し、判定を保留（pass: false / 理由: 環境未整備）にすること。勝手に別手段で「動いてそう」と判断しない。

これを書く前は、ブラウザが使えない状況でHTMLをテキストとして読み、「構造上は問題なさそうです」と返してくることがありました。悪意はなく、頼まれた仕事を何とか果たそうとしているだけです。だからこそ「できませんでした」と言ってよい、と明示的に許可しておく必要がありました。検証の穴として一番危ないのは、失敗ではなく、失敗が成功のふりをすることです。

06運用して分かった4つのこと

1. 検証を回すタイミングは、人間が決める

最初は Generator が終わるたびに自動で Evaluator を走らせていました。これは失敗でした。デザインを速く回している最中は、1スプリントごとの本検証はコストにも時間にも重すぎて、結局こちらが途中で止めることになる。今は Generator が終わったら変更点と自己チェックだけを受け取り、本検証を回すか、次に進むか、ここで終えるかは人間が判断します。ハーネスは自動化のためではなく、品質のためにあります。

2. 仕様変更は必ず Planner に戻す

作っている途中で仕様を変えたくなったとき、Generator に直接直させると、その瞬間に SPEC.md と実装が乖離します。乖離した仕様書で Evaluator が判定すると、正しい実装が「不合格」になる。遠回りに見えても、仕様変更は Planner に差し戻して SPEC.md を更新し、改訂履歴を残してから実装に降ろします。

3. 踏んだ罠は、その場で外部に書き出す

セッションが変われば文脈は消えます。一度踏んだバグを二度踏まないためには、プロジェクトごとのメモリーに残すしかない。実際に残しているものの例を挙げると、単体HTMLのビルドスクリプトで String.replace の置換文字列にバンドルを差し込むと、コード中の $$ が $ に化けて構文エラーになる（置換は関数で渡す）、といった類のものです。この手の罠は、原因を知っていれば5分、知らなければ半日溶けます。

4. 3体で足りないときは、壊しに行かせる

Planner → Generator → Evaluator は「仕様どおりに動くか」を保証する流れであって、「仕様が想定していない壊し方」までは見ません。そこは別途、複数のエージェントに意図的に反証させるレビューを回して硬化させます。作る流れと壊す流れは、別の工程として持っておく方が素直でした。

07道具ではなく、体制の話

この構成に特別な技術は入っていません。Markdown が3枚と、ブラウザを動かすための MCP がひとつあるだけです。効いているのは、誰が何を書けて、何を書けないかを先に決めたことだけだと思っています。

仕様を書く人がコードを触れない。作る人が仕様を書き換えられない。判定する人が直せない。この3つを守ると、AIに任せられる範囲がはっきりと広がりました。逆に言えば、この境界を引かずに「AIで速く作れます」と言うのは、少し無責任だとも思っています。速さは、あとから直す時間まで含めて数えないと意味がないので。

LiberaSpace の制作物は、この流れを通したうえでお渡ししています。同じやり方が全部の案件に最適だとは思っていませんが、少なくとも「動いてそう」を納品しないための仕組みとしては、いまのところこれが一番うまくいっています。
